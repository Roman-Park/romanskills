# Usertest

만든 사람은 "정상 경로"만 밟아 보기 쉽고, 코드를 읽는 것만으로는 실제 사용 중에 깨지는 지점이 보이지 않는다. 그래서 코드 관점이 아니라 **처음 써 보는 사용자**의 입장에서 결과물을 직접 움직여 본다. 이 스킬은 문제를 찾아서 **보고**하는 것까지가 일이다. 수정은 사용자 승인 후에 한다. 코드 관점의 재검토는 `crosscheck`의 몫이고, 여기서는 하지 않는다.

## Workflow

1. **Who & what**: 이번 작업이 사용자에게 보이는 것(화면, 명령, 응답, 문구)이 무엇이고 누가 어떤 목적으로 쓰는지 한두 줄로 정한다. 사용자에게 보이는 변화가 없으면 그 사실을 알리고 멈춘다.
2. **Scenarios**: 사용자가 실제로 할 행동을 시나리오로 적는다. 대표 흐름 1~2개와, 사용자가 흔히 저지르는 행동(빈 값 제출, 잘못된 형식, 연타, 뒤로 가기·새로고침, 중간에 취소, 너무 긴 입력, 처음 사용하는 상태)을 섞는다. 시나리오는 단계별로 "무엇을 하면 무엇이 보여야 하는가"까지 적는다.
3. **Run**: 가능하면 결과물을 실제로 실행해서 시나리오를 그대로 따라간다. 웹은 브라우저(미리보기 도구)로 열어 클릭·입력하고, 모바일 앱은 시뮬레이터로, CLI나 API는 실제 명령과 요청으로 확인한다. 개발 서버가 필요하면 띄운다. 실행할 수 없는 환경이면 그 사실을 밝히고, 코드와 화면 정의를 읽으며 시나리오를 머릿속으로 따라가는 방식으로 대신하되 "실행하지 못함"으로 표시한다.
4. **Look**: 각 단계에서 사용자가 보게 되는 것을 점검한다.
   - 동작: 기대한 결과가 나오는가, 오류나 멈춤, 콘솔 에러가 없는가
   - 화면: 깨진 레이아웃, 모바일 폭, 잘리거나 겹치는 요소, 로딩·빈 상태
   - 문구: 오류 메시지와 안내가 사용자가 이해하고 다음 행동을 알 수 있게 쓰였는가
   - 접근성: 키보드로 조작 가능한가, 버튼과 입력에 이름이 있는가, 대비와 글자 크기가 충분한가
   웹이면 스크린샷이나 페이지 텍스트로 눈으로 확인한 것을 근거로 삼는다.
5. **Report**: 아래 형식으로 보고하고 멈춘다.

## Report format

```
## Usertest 결과
**결론**: 문제 없음 | 확인 필요 N건 | 수정 필요 N건

**테스트한 시나리오**: 시나리오별 한 줄 + 통과/실패/실행 못 함
**발견한 문제** (심각도 높은 순)
- [높음/중간/낮음] 무엇이 문제인가 — 재현 단계(1. … 2. …), 기대한 것, 실제로 본 것
**확인하지 못한 것**: 실행 못 한 시나리오와 그 이유
```

문제가 없으면 문제 없다고 분명히 쓴다. 발견한 문제가 있으면 마지막에 수정할지 AskUserQuestion으로 묻는다.

## Principles

- 사용자는 코드를 모른다. 내부 구조를 아는 사람만 이해하는 흐름이나 문구는 그 자체로 문제다.
- 재현 단계가 없는 문제는 보고하지 않는다. 직접 본 것과 추측을 구분해서, 추측은 "확인하지 못한 것"에 둔다.
- 실행하지 않은 시나리오를 통과했다고 쓰지 않는다.
- 테스트하면서 만든 데이터나 상태(테스트 계정, 임시 파일)는 사용자의 실제 데이터와 섞이지 않게 하고, 끝나면 정리하거나 남겼다고 알린다. 결제, 메시지 발송처럼 되돌릴 수 없는 동작은 실제로 실행하지 않고 테스트용 환경이 있을 때만 한다.
- 검증 중에 코드를 고치지 않는다. 고치면 검증 대상이 바뀌어서 앞선 결과가 무효가 된다. 승인 후 고치고 해당 시나리오만 다시 돌린다.
- 범위는 이번 작업이 바꾼 것과 그 주변의 사용자 흐름까지다. 제품 전체 QA로 넓히지 않는다.
