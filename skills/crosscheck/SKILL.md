# Crosscheck

작업을 끝낸 직후의 판단은 "내가 의도한 대로 만들었다"는 기억에 기대기 쉽다. 그래서 만든 사람의 시선을 내려놓고, 변경분을 처음 보는 리뷰어처럼 다시 확인한다. 이 스킬은 문제를 찾아서 **보고**하는 것까지가 일이다. 수정은 사용자 승인 후에 한다.

## Workflow

1. **Scope**: 이번 작업에서 실제로 바뀐 것을 확정한다. git 저장소면 `git status`와 `git diff`로, 아니면 대화에서 수정한 파일 목록으로 확인한다. 변경 파일과 함수를 짧게 나열한다. 변경이 없으면 그 사실을 알리고 멈춘다.
2. **Requirement**: 사용자가 원래 요청한 내용을 항목별로 뽑아 변경분과 하나씩 대조한다. 빠진 항목, 요청하지 않았는데 추가된 변경(범위 초과)을 찾는다.
3. **Re-read**: 변경된 코드를 다시 읽으며 로직 오류, 엣지 케이스(빈 값, null, 경계값, 에러 경로), 오타, 잘못된 이름·경로, 처리되지 않은 예외를 찾는다. 작성할 때 가정한 것이 실제 코드나 데이터와 맞는지 열어서 확인한다.
4. **Impact**: 바뀐 함수, 모듈, 설정, 스키마, 파일 이름을 검색(Grep 등)해서 그것을 쓰는 곳을 모두 찾는다. 호출부가 바뀐 시그니처·반환값·동작에 여전히 맞는지, 공유 상태나 설정을 바꿔서 다른 기능이 영향을 받지 않는지 확인한다.
5. **Run**: 프로젝트에 있는 테스트, 린트, 타입 체크, 빌드를 실제로 실행한다. 어떤 명령이 있는지는 package.json, Makefile, README, CI 설정에서 찾는다. 실행 수단이 없으면 "실행할 수 있는 검증이 없었다"고 밝히고, 변경 동작을 확인할 가장 작은 방법(스크립트 한 번 돌리기 등)이 있으면 그것을 쓴다. 실패하면 이번 변경 때문인지, 원래 있던 실패인지 구분한다.
6. **Report**: 아래 형식으로 보고하고 멈춘다.

## Report format

```
## Crosscheck 결과
**결론**: 문제 없음 | 확인 필요 N건 | 수정 필요 N건

**검증한 범위**: 변경 파일, 대조한 요청 항목, 실행한 명령
**발견한 문제** (심각도 높은 순)
- [높음/중간/낮음] 위치(파일:줄) — 무엇이 문제이고 어떤 상황에서 깨지는지
**확인하지 못한 것**: 실행 못 한 검증, 근거가 부족해 추측으로 남은 부분
```

문제가 없으면 문제 없다고 분명히 쓴다. 발견한 문제가 있으면 마지막에 수정할지 AskUserQuestion으로 묻는다.

## Principles

- 문제를 억지로 만들지 않는다. 근거(코드 위치, 실행 결과, 재현 조건)가 있는 것만 문제로 쓰고, 근거 없는 의심은 "확인하지 못한 것"에 따로 둔다. 가짜 경고가 많으면 진짜 경고가 묻힌다.
- 실행하지 않은 것을 통과했다고 쓰지 않는다. 테스트를 돌렸으면 명령과 결과를, 안 돌렸으면 안 돌렸다고 적는다.
- 검증 중에 코드를 고치지 않는다. 고치는 순간 검증 대상이 바뀌어서 앞서 확인한 것이 무효가 된다. 사용자가 승인하면 고친 뒤 영향받은 부분만 다시 확인한다.
- 변경과 무관한 기존 문제는 발견해도 본론과 섞지 않고 한 줄로만 따로 언급한다.
- 범위는 이번 작업의 변경분과 그 영향 범위까지다. 저장소 전체 감사로 넓히지 않는다.
